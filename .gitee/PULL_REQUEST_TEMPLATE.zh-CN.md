# 项目/模块 - PR类型
*示例： 【# BugCapsule - 缺陷修复】 或 【# BugCapsule - 功能新增】*

---

## 📝 简述（一句话概括）
> 本 PR 主要：________________________  
> *示例：修复登录 token 刷新时偶发失效的问题，并增加重试机制。*

---

## 📋 基本信息
- **关联 Issue**：`#编号` （若无，请说明需求来源或问题背景）
- **PR 类型**：`功能新增` / `缺陷修复` / `性能优化` / `代码重构` / `文档更新` / `构建/依赖调整`

---

## 🎯 变更目的（为什么做）
> 详细描述要解决什么问题、达成什么目标，补充简述中的背景。

---

## 🔧 具体变更（做了什么）
- 按模块/文件列出主要改动点：
  - `path/file`：调整了 xxx 逻辑，原因/效果。
  - 若涉及数据库、配置、API 兼容性，请特别说明。
- **破坏性变更**：是 / 否（如是，需附迁移方案）

---

## ✅ 测试验证（如何保证质量）
- [ ] 单元测试：新增 / 修改 / 无需（通过数 __，覆盖率 __%）
- [ ] 集成测试：已覆盖关键链路（如：登录→操作→登出）
- [ ] 手工验证场景（正常 / 异常 / 边界）：
  - 正常流程：...
  - 异常场景：超时、网络错误、权限不足等
  - 边界值：空数据、大并发等
- [ ] 回归影响：列出可能受影响的现有功能，确认无退化

---

## 📎 补充说明（可选）
- 依赖的外部变更（如升级第三方库、数据库迁移）
- 待办事项 / 后续优化计划
- 截图、日志或性能数据

---

## 🧾 提交前自检清单（请逐项勾选）
- [ ] 代码已通过 lint 和构建
- [ ] 无调试代码、日志清晰、命名规范
- [ ] 文档（README / API / 部署）已同步更新（如需要）
- [ ] 未引入安全隐患（密钥、注入、XSS 等）
- [ ] 已 rebase 最新主干，无冲突
- [ ] PR 标题符合规范（如 `[FEAT]` / `[FIX]` / `[REFACTOR]`）
